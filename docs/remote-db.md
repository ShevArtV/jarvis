# Удалённая БД Jarvis (libSQL / sqld)

`bot_state.db` можно держать не локальным файлом SQLite, а в сетевой БД
**libSQL/sqld**. Тогда инстансы на разных машинах ходят в ОДНУ историю и
взаимозаменяемы — это и есть «развернуть Jarvis на любой машине».

Дефолт не меняется: без настройки бот работает с локальным файлом `bot_state.db`,
как раньше. Удалённый режим включается тремя переменными окружения.

## Выбор бэкенда

| Переменная | Значение |
|---|---|
| `JARVIS_DB_BACKEND` | `sqlite` (дефолт) или `libsql` |
| `JARVIS_DB_URL` | `https://<ваш-sqld-хост>` (для `libsql`) |
| `JARVIS_DB_AUTH_TOKEN` | JWT доступа к sqld — из секрет-хранилища, **НЕ в репозиторий** |

Для `libsql` нужен пакет `turso_serverless` (уже в `requirements.txt`; чистый
Python DB-API, ставится на 3.14 без Rust — в отличие от нативного `libsql`).

Код: `bot/db_backends.py` — слой совместимости идиом `sqlite3` ↔ sqld (строки с
доступом по имени, перевод исключений в `sqlite3.OperationalError`, глушение
`PRAGMA journal_mode`). Точки выбора бэкенда — `bot/db.py` и
`mcp_server/common.py` (ветка remote первой, иначе прежний локальный sqlite3).

## Ограничение: один поллер на токен

У Telegram один `getUpdates`-поллер на токен бота. Поэтому против общей БД в
каждый момент работает **ОДИН** инстанс (два живых бота на одном токене → `409
Conflict`). «Взаимозаменяемы» = по очереди, не параллельно. **Перед запуском
инстанса на новой машине остановите прежний.**

## Инструкция агенту: миграция истории `bot_state.db` → sqld

Скрипт: `scripts/migrate_to_sqld.py`.

### Шаг 1. Снять консистентный снимок (на машине с боевым `bot_state.db`)

Бот пишет в файл непрерывно. Остановите бота, затем снимите снимок одной
командой — она корректно вбирает WAL (`-wal`/`-shm`):

```bash
sqlite3 bot_state.db ".backup /tmp/bot_state.snapshot.db"
```

> Не копируйте «живой» `bot_state.db` без остановки бота и без `.backup` — часть
> истории останется в WAL и потеряется.

Передайте `/tmp/bot_state.snapshot.db` на машину, с которой будете заливать.

### Шаг 2. Залить снимок в sqld

На любой машине с доступом к sqld и к файлу снимка:

```bash
JARVIS_DB_URL=https://<ваш-sqld-хост> \
JARVIS_DB_AUTH_TOKEN=<JWT> \
python scripts/migrate_to_sqld.py --source /path/to/bot_state.snapshot.db --reset
```

- `--reset` — снести таблицы назначения и залить заново (чистая миграция; нужно
  при первом переносе, т.к. бот/`init_db` мог создать там пустую схему).
- Скрипт: воссоздаёт схему из источника (таблицы + индексы) → пакетно копирует
  строки, **сохраняя первичные ключи** (id сеансов/job'ов/ask остаются прежними)
  → сверяет число строк по каждой таблице (источник == sqld).
- Успех: вывод `=== МИГРАЦИЯ ЗАВЕРШЕНА ===` и код возврата `0`. Любое
  `!! РАСХОЖДЕНИЕ` — не переключать инстанс, разбираться.

Сухой прогон без сети (проверить логику на копии): укажите в `JARVIS_DB_URL`
путь к `.db`-файлу вместо `http(s)` — назначением станет локальный sqlite.
Флаг `--dry-run` только печатает план, ничего не пишет.

### Если снимок крупный

Копирование идёт через публичный HTTPS. Для большого `messages_log` быстрее
залить через локальный порт sqld (SSH-форвард к `127.0.0.1:8080` сервера) —
`JARVIS_DB_URL=http://127.0.0.1:<локальный-порт>`; результат тот же.

## Инструкция агенту: переключить инстанс на удалённую БД

1. В `.env` инстанса выставить:
   ```
   JARVIS_DB_BACKEND=libsql
   JARVIS_DB_URL=https://<ваш-sqld-хост>
   JARVIS_DB_AUTH_TOKEN=<JWT>
   ```
2. Убедиться, что прежний инстанс (на другой машине) **остановлен** — один токен.
3. Запустить бота обычным способом (Linux — systemd; Windows — см.
   [`docs/windows.md`](windows.md)). `init_db` идемпотентен: создаст недостающее,
   уже мигрированные данные не перезапишет.

## Откат на локальный sqlite

Убрать `JARVIS_DB_BACKEND` (или выставить `=sqlite`) и перезапустить — бот снова
работает с локальным файлом `bot_state.db`. Данные, записанные в sqld за время
удалённого режима, в локальный файл сами не вернутся: при необходимости выгрузить
обратно отдельным прогоном (поменяв местами источник и назначение вручную).

## Безопасность

- JWT и приватный ключ sqld — в секрет-хранилище, **НЕ в репозиторий**. В `.env`
  токен лежит локально (права `0600` / ACL профиля на Windows).
- Публичный ключ sqld (`SQLD_AUTH_JWT_KEY`) — в env контейнера на сервере.
- Ротация при утечке токена: сгенерировать новый ключ Ed25519, обновить
  `SQLD_AUTH_JWT_KEY` в env контейнера, выпустить новый JWT, разложить по `.env`
  инстансов.
